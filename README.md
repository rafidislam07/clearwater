# Presentation webpage — implementation notes

Plain HTML/CSS/JS, no build step, no framework. Run locally with any static server,
e.g. `python3 -m http.server 8000` from this directory, then open `index.html`.

## Architecture

- **`js/data.js`** — the only place content lives: buy-box specs, comps, revenue
  tiers, Alexandria link fields, analyst notes, map config. Nothing else in the
  codebase hardcodes buy-box content.
- **`js/render.js`** — presentation logic. Builds every DOM component from `data.js`,
  including the reusable buy-box deep-dive (`renderDeepDive`, sections A-N) used
  identically by every buy box, developed or pending.
- **`js/charts.js`** — Chart.js chart rendering (demographics, property size).
- **`js/map.js`** — Leaflet/OpenStreetMap interactive map, reading `data/listings.json`.
- **`js/main.js`** — bootstraps everything on `DOMContentLoaded`; nav scroll-spy;
  lightbox open/close wiring (click-outside and Escape).
- **`css/styles.css`** — the whole design system (tokens, layout, responsive
  breakpoints at 960px/600px).
- **`data/listings.json`** — generated by `../scripts/generate_webpage_map_data.py`
  from the cleaned market CSV; safe to re-run.
- **`assets/<buy-box>/<category>/`** — real supplied photography, one directory per
  buy box that has real photos. Each has a `SOURCE.md` documenting where every file
  came from. Buy boxes with no stored photos yet (currently 4BR) use a "photo
  pending — view on Airbnb" placeholder instead (see `imagePlaceholder` in render.js).

## Two image-reference shapes (see `renderImage` in render.js)

1. A bare property-ID string (e.g. `"abnb_568002792449614181"`) → renders a pending
   placeholder linking to the real Airbnb listing. Used where no photo is stored yet.
2. A `photo(relPath, alt, caption)` object (see the helper at the top of `data.js`)
   → renders a real `<img>` with lazy loading, alt text, and a caption, opening the
   shared lightbox on click. Used wherever real supplied photography exists.

Both shapes can be mixed freely inside the same field (e.g. `images: [...]` arrays);
`renderImage`/`renderImageGrid` dispatch on the type automatically.

## Two comp-set shapes (legacy design section K, revenue tiers in section M)

These two shapes power the **legacy A-N structure** (currently used only by
3BR; see the BuyBox Template V.2 section below for 4BR's current approach):

- **Identified comps** (`box.designComps`, `tier.comps`): named Airbnb listings with
  a URL and metrics (revenue/ADR/occupancy/etc.) — rendered as `compCard`s.
- **Anonymous photo evidence** (`box.designPhotos`, `tier.photos`): supplied
  photography with no identified listing behind it — rendered as a photo gallery.
  Used by 3BR, whose source package supplied representative photos only, with no
  Airbnb listing names/URLs/metrics for any comp.

Never mix the two within one buy box's design section or one revenue tier — pick
whichever shape matches what the source material actually supports. (4BR's own
11-comp evidence table now uses a third, even leaner shape — see
`bb2CompTable` below — since its "Projections & Revenue Comps" section needs a
compact table, not full comp-card write-ups.)

## 4BR's BuyBox Template V.2 deep dive (2026-08-24)

4BR's `BUY_BOXES` entry sets `narrative: true` and `buyBoxSections` (an ordered
array of block-key strings mapping to BuyBox Template V.2's fields).
`renderDeepDive` in render.js checks for this and, when present, renders
exactly those blocks in that order via a `NARRATIVE_BLOCKS` dispatch table,
instead of the fixed legacy A-N sequence below. 4BR's order is: Buy-Box
Overview → STR Regulations → Property Profile → Amenities → Geo & Property
Location → Traveler Demographic → Design Playbook → Projections & Revenue
Comps → Analyst Notes → Purchase Price. Every block builder (`bb2OverviewBlock`,
`bb2RegulationsBlock`, `bb2PropertyProfileBlock`, `bb2AmenitiesBlock`,
`bb2GeoBlock`, `bb2TravelerDemoBlock`, `bb2DesignPlaybookBlock`,
`bb2ProjectionsBlock`, `analystNotesV2Block`, `acquisitionV2Block`) is a small,
generic function built from the same shared helpers used everywhere else on
the page (`ddBlock`, `renderImage`, `alexandriaButton`, `pendingBadge`) — none
of it is 4BR-specific markup. A buy box that omits `narrative`/
`buyBoxSections` (3BR, and any future data-only buy box) automatically falls
through to the legacy A-N structure unchanged, using the original
`identityBlock`/`purchasePriceBlock`/`analystNotesBlock` functions (still
present, still 3BR's exact code path).

This redesign replaced an earlier, more report-like "show, don't tell" flow
(buy-box answer → target product → revenue-comp proof → strong visual
mechanisms → weak execution → premium ideas → acquisition status) that
organized the page around the analytical workflow rather than the client-facing
buy-box template. No underlying data was discarded in the rewrite — the same
11-comp revenue set, 8-property design/reference set, and 19 images are all
still present, just reorganized and de-duplicated (each image now has one
primary presentation role; see `revenueComps11` in data.js, which intentionally
carries no `image` field per comp anymore — the full evidence table is
text/link-only, since photos already appear once each in the Design Playbook).

### New presentation components (`bb2-*` CSS classes, scoped under `.bb2`)

- `.bb2-hero` — the Section-1 hero card (image + status badge + chips).
- `.bb2-chip` / `.bb2-chip--revenue` — pill-style summary facts.
- `.bb2-grid-2`, `.bb2-amenity-row` — the two-column must-have/nice-to-have
  amenity lists with inline thumbnails.
- `.bb2-playbook-grid`, `.bb2-mechanism-card` — the Design Playbook's
  one-mechanism-per-property image cards.
- `.bb2-stat-row`, `.bb2-stat` — the compact revenue summary numbers.
- `.bb2-details` (native `<details>`/`<summary>`) + `.bb2-comp-table` — the
  "View all 11 revenue comps" expandable evidence panel, rendered as a plain
  table (no repeated property images).
- `ddBlock`'s existing `variant` param (`"contrast"`, `"premium"`, and now also
  `"compact"`) still drives the low-tier-contrast, premium, and
  regulations/geo/traveler-demographic visual treatments.
- `.container:has(.bb2) { max-width: 1400px; }` widens only the specific
  `.container` that actually holds `.bb2` content (i.e. only while the 4BR tab
  is showing) — self-scoping via `:has()`, with zero effect on 3BR's identical
  `.container` element when its tab is active.

## Adding 5BR

Add a new object to `BUY_BOXES` in `data.js` using the exact same shape as the 3BR
or 4BR entry (whichever comp-set shape matches the 5BR source material), then flip
`status` to `"developed"`. No component code needs to change — `render.js` is fully
data-driven. Fields with no source-material answer should be omitted (left
`undefined`) rather than guessed; `ddBlock` automatically skips rows with no value.

## Adding Alexandria links

Each developed buy box has `alexandria: { designCompSetUrl, revenueCompSetUrl }` in
`data.js`. Both are `null` for every buy box as of 2026-08-23 (no real Alexandria
links have been supplied for either 3BR or 4BR). Fill in the URL string(s) once
available — the "Open Design/Revenue Comp Set in Alexandria" buttons pick this up
automatically and stop showing the "(pending)" disabled state.

## 4BR photography and asset architecture (2026-08-23)

4BR now has real stored photography under `assets/4br/`, organized by role:

- `assets/4br/core-comp-set/<property>/` — the 3 official core comps (Pink Paradise,
  Lost in Paradise, Clearwater GLAM).
- `assets/4br/supporting-comp-set/<property>/` — secondary/bridge comps (Movie
  Oasis, Flamingo Oasis, Tropical Family Villa).
- `assets/4br/premium-references/<property>/` — the "High-Capacity Group Resort
  House" premium-variant references (Palm Palms, Tiki) — kept visually and
  structurally separate from the core buy box.
- `assets/4br/low-tier-counterexamples/` — the "What Weak Execution Looks Like"
  section (3 images, all from a single listing, `abnb_43358269`).

19 images total, copied from `rafid/Clearwater_Buy_Box_4BR/` and re-encoded
following the same convention as 3BR (max 1600px long edge, JPEG q78, no
upscaling). See `assets/4br/SOURCE.md` for the full provenance map (original
path, property/ID, role, visible subject, approved caption, and any caution or
prohibited claim per image), and `rafid/Clearwater_Buy_Box_4BR/asset_manifest.csv`
/ `FINAL_IMAGE_VERIFICATION.md` for the underlying verification record.

## Adding more 4BR photography

To add more images later: copy files into the relevant `assets/4br/<role>/<category>/`
folder with clean filenames, add a row to `assets/4br/SOURCE.md` (see its existing
rows for the pattern), then reference the file from `data.js` with `photo(...)`.
Bare property-ID string placeholders (`imagePlaceholder` in render.js) are still
used for the 5 of 11 revenue comps in `revenueComps11` that have no stored photo
yet — this is expected, not a bug (see `revenueProofBlock` in render.js).

## 3BR integration (2026-08-23)

3BR content was integrated from a supplied package
(`~/repos/clearwater/walid/Clearwater_Buy_Box_3BR/` — a DOCX plus 9 image folders).
See `assets/3br/SOURCE.md` for the full file-by-file asset mapping, and the
"Presentation Webpage" section of the root `LLM_CONTEXT.md` for what is
populated vs. pending. In short: every 3BR field on the page traces directly to
that DOCX's own table or its supplied folder images; fields the DOCX left
unanswered (property type name, evidence for bedroom/bath beyond the stated
range, occasion demand, specific comp identities/links, STR regulation
determination) were omitted rather than guessed, per the DOCX's own template
structure being left blank for those rows.
